## 1. Final System Architecture

<img width="1880" height="450" alt="Final Vivado Block Design" src="https://github.com/user-attachments/assets/b517330d-5cb6-438a-b1ac-1944311ed069" />

The final CNN accelerator was developed and verified through two main stages: **Vitis HLS** and **Vivado system integration**.

### Vitis HLS

- CNN implementation in C/C++
- Functional verification using C Simulation
- Resource optimization
- Export of the optimized CNN accelerator as a Vivado IP

### Vivado

- Integration of the CNN accelerator with the Zynq UltraScale+ MPSoC
- AXI-based memory interface construction
- DDR-based input/output storage
- BRAM-based weight and bias storage
- AXI transaction and output verification

### Final Verification Flow

```text
Initialize CNN weights and biases in BRAM using COE
                        ↓
Initialize input feature data in DDR
                        ↓
Configure CNN accelerator registers through AXI-Lite
                        ↓
Start CNN accelerator
                        ↓
CNN reads:
  - Input data from DDR
  - Weights and biases from BRAM
                        ↓
CNN computation
                        ↓
Output logits written to DDR
                        ↓
Read output logits
                        ↓
Compare RTL simulation results with CPU golden values
```

| FF | 234,240 | 116,158 | 49.6% | 79,820 | 34.1% | -31.3% |
| DSP | 1,248 | 1,006 | 80.6% | 1,132 | <span style="color:red"><b>90.7%</b></span> | +12.5% |

| URAM | - | 0 | - | 0 | - | - |

The comparison shows that the resource estimation from Vitis HLS can differ significantly from the post-synthesis utilization reported by Vivado.

In particular:

- LUT utilization decreased by approximately **33.9%**
- FF utilization decreased by approximately **31.3%**
- BRAM usage decreased by approximately **59.5%**
- DSP utilization increased by approximately **12.5%**

This demonstrates the importance of evaluating resource utilization after RTL synthesis rather than relying only on HLS estimates.

## 4. Vivado Full-System Verification

The complete accelerator system is verified using Vivado behavioral simulation.

### Memory Architecture

The final system separates dynamic input/output data from fixed CNN parameters.

```text
                         CNN Accelerator
                        /               \
                       /                 \
              DDR Interface          BRAM Interface
                    |                      |
              SmartConnect           SmartConnect
                    |                      |
          PS S_AXI_HP0_FPD       AXI BRAM Controller
                    |                      |
                   DDR                Block Memory
                  /   \                    |
             Input   Logits        Weights / Biases
```
*PS S_AXI_HP0_FPD is PS side AXI Slave port

### DDR

DDR stores data that changes for each CNN execution:

- CNN input feature data
- Output logits

### BRAM

BRAM stores fixed CNN parameters:

- Convolution weights
- Fully connected weights
- Bias values

The BRAM contents are initialized before simulation using a **COE file**.

---

## 5. BRAM Weight Initialization

CNN weights and biases are stored in a single contiguous BRAM address space.

The parameters are generated using the same deterministic random-number sequence used by the CPU reference implementation.

The generated parameters are packed into 32-bit words and stored in a COE initialization file.

```text
COE File
   ↓
Block Memory Generator
   ↓
BRAM
   ↓
AXI BRAM Controller
   ↓
SmartConnect
   ↓
CNN Accelerator
```

This removes the need to initialize all CNN parameters through DDR during simulation and allows the CNN accelerator to directly access pre-initialized model parameters.

## 6. Vivado Simulation Sequence

The full-system testbench performs the following sequence:

```text
1. Pre-initialize CNN weights and biases in BRAM using all_weights.coe
                        ↓
2. Initialize CNN input data in DDR using deterministic test vectors
                        ↓
3. Clear the DDR output region for logits
                        ↓
4. Configure CNN AXI-Lite registers
   - Input pointer
   - Weight / bias pointers
   - Output logits pointer
   - Quantization shift values
                        ↓
5. Read back selected AXI-Lite registers to verify address configuration
                        ↓
6. Assert ap_start to start the CNN accelerator
                        ↓
7. CNN reads input feature data from DDR
                        ↓
8. CNN reads pre-initialized weights and biases from BRAM
                        ↓
9. CNN performs inference through the complete CNN pipeline
                        ↓
10. CNN writes the two output logits to DDR through AXI
                        ↓
11. Monitor CNN-side and PS S_AXI_HP0_FPD-side AXI write transactions
                        ↓
12. Compare the captured output logits with the CPU golden values
                        ↓
13. Read the DDR output region as an additional diagnostic check
                        ↓
14. Report CNN output verification and per-layer/phase timing results
```

### Final Comparison
| Implementation | Architecture | Clock | Latency | Relative to DPU |
|---|---|---:|---:|---:|
| **Reference Paper** | DPUCZDX8G B4096 | 300 MHz | **0.876 ms** | **1.00×** |
| Custom CNN - HLS Estimate | Vitis HLS Accelerator | 100 MHz | 2.963 ms | 3.38× |
| **Custom CNN - RTL DATAFLOW** | Vitis HLS Accelerator | 100 MHz | **2.535 ms** | **2.89×** |
| Custom CNN - Full RTL | HLS + AXI + Memory System | 100 MHz | 5.969 ms | 6.81× |

But when it comes to cycles... Our custom hardware is better.
| Implementation | Clock | Latency | Approx. Cycles |
|---|---:|---:|---:|
| Reference DPU B4096 | 300 MHz | **0.876 ms** | ~262,800* |
| **Custom RTL DATAFLOW** | 100 MHz | **2.535 ms** | **253,502** |

So, final comparison is... 
| Platform | Implementation | Precision | Clock | Latency | Throughput |
|---|---|---|---:|---:|---:|
| ARM Cortex-A53 | Reference CPU | FP32 | - | 6.470 ms | 154.6 FPS |
| ARM Cortex-A53 | Reference CPU | INT8 | - | 6.380 ms | 156.7 FPS |
| **Kria KV260** | **Reference DPU B4096** | **INT8** | **300 MHz** | **0.876 ms** | **1140+ FPS** |
| **Kria KV260** | **Custom HLS RTL DATAFLOW** | **INT8** | **100 MHz** | **2.535 ms** | ~394 FPS* |
| **Kria KV260** | **Custom Full RTL** | **INT8** | **100 MHz** | **5.969 ms** | ~168 FPS* |

Therefore, the current primary optimization target is the **weight / bias loading path**, followed by improving the achievable operating frequency of the custom accelerator.

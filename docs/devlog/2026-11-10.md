
# Convolution Block 3 — LUT Optimization

## 1. Baseline vs. Hardware Reuse

To reduce hardware resource utilization, partial hardware reuse was introduced in Convolution Block 3.

### Performance Comparison

| Metric | Baseline | Reuse 16/32 | Change |
|:---|---:|---:|---:|
| Total Latency | 1.730 ms | 2.603 ms | +50.5% |
| Pipeline Latency | 1.175 ms | 2.048 ms | +74.3% |
| Pipeline Interval (cycles) | 117,505 | 204,814 | +74.3% |
| Weight Loading | ~0.553 ms | ~0.553 ms | No change |

### Observations

- Hardware reuse increased total latency by **50.5%**.
- Pipeline latency and interval increased by approximately **74.3%**.
- Weight loading latency remained unchanged.
- Despite reducing parallelism, **LUT utilization remained relatively high**.

> [!IMPORTANT]
> **Problem:** Hardware reuse alone was insufficient to achieve the desired LUT utilization.
>
> **Objective:** Further reduce LUT usage through arithmetic bitwidth optimization and weight memory restructuring.

---

## 2. Optimization 1 — Narrow-Width MAC Accumulation

### Motivation

The original MAC implementation used `int32_t` for intermediate calculations, even though both input activations and weights were represented as signed 8-bit integers.

Using unnecessarily wide accumulators may increase the hardware resources required for arithmetic operations.

### Original Implementation

```cpp
int32_t channel_sum = 0;

for (int k = 0; k < 9; ++k) {
#pragma HLS UNROLL

    const ap_uint<8> raw =
        pkt.range(8 * k + 7, 8 * k);

    const ap_int<8> x = (ap_int<8>)raw;
    const int32_t w =
        (int32_t)weights[k][ic * CONV3_2_OUT_C + oc];

    channel_sum += (int32_t)x * w;
}
```

### Modified Implementation

```cpp
// (heewon) Narrow-width MAC accumulation
ap_int<19> channel_sum = 0;

CONV3_2_REUSE_MAC9:
for (int k = 0; k < 9; ++k) {
#pragma HLS UNROLL

    const ap_uint<8> raw =
        pkt.range(8 * k + 7, 8 * k);

    const ap_int<8> x = (ap_int<8>)raw;
    const ap_int<8> w =
        (ap_int<8>)weights[k][ic * CONV3_2_OUT_C + oc];

    channel_sum += x * w;
}
```

### Bitwidth Analysis

Each channel performs nine signed INT8 multiplications.

- Input activation: 8-bit signed integer
- Weight: 8-bit signed integer
- Multiplication result: up to 16 bits
- Number of MAC operations: 9

The maximum positive product of two signed INT8 values is:

\[
(-128)\times(-128)=16,384
\]

Therefore, the maximum positive accumulation is:

\[
9\times16,384=147,456
\]

A signed 19-bit integer supports:

\[
-262,144 \leq x \leq 262,143
\]

Thus, **19 bits are sufficient** for the nine-product channel accumulation.

**Change:** `int32_t` → `ap_int<19>`

## 3. Optimization 2 — Narrow-Width Partial Sums

### Motivation

The original implementation also used 32-bit integers for partial sums and phase accumulation.

Since the intermediate arithmetic range is bounded, these data types can be narrowed without losing precision within the specified MAC operation.

### Original Implementation

```cpp
int32_t partial[32];
int32_t phase_sum = 0;
```

### Modified Implementation

```cpp
// (heewon) Narrow-width partial sums
ap_int<19> partial[32];
ap_int<24> phase_sum = 0;
```

### Bitwidth Analysis

**1. Partial Sum**

Each partial sum represents nine INT8 multiplication results.

As calculated previously, 19 bits are sufficient.

```cpp
ap_int<19> partial[32];
```

**2. Phase Sum**

The phase accumulator combines 32 partial sums.

Since each partial sum fits within 19 bits, accumulating 32 values requires up to five additional bits:

\[
19+\log_2(32)=24\text{ bits}
\]

Therefore:

```cpp
ap_int<24> phase_sum = 0;
```

### Summary

| Variable | Original | Optimized |
|:---|:---:|:---:|
| Input activation | 8-bit | 8-bit |
| Weight operand | 32-bit cast | 8-bit |
| Channel accumulation | 32-bit | **19-bit** |
| Partial sum | 32-bit | **19-bit** |
| Phase accumulation | 32-bit | **24-bit** |

> [!NOTE]
> These widths are sufficient for the specified intermediate operations. The complete 64-channel accumulation and bias addition must still use sufficient precision to preserve numerical correctness.

## 4. Optimization 3 — Weight Memory Banking

### Motivation

Reducing arithmetic bitwidth alone may not sufficiently reduce LUT utilization because memory access and multiplexing logic can also consume substantial LUT resources.

To address this, weight memory banking was applied to reorganize weight storage and access.

### Observations

- Weight memory banking **significantly reduced LUT utilization**.
- However, BRAM consumption increased substantially.
- The resulting BRAM utilization **exceeded the available hardware budget**.

> [!WARNING]
> **Resource Trade-off**
>
> Although weight banking successfully reduced LUT usage, the increased BRAM consumption made the resulting architecture infeasible for the target FPGA.

### Implications

The experiment revealed a trade-off between LUT and BRAM utilization.

- More aggressive memory banking can reduce some multiplexing overhead.
- However, excessive partitioning or inefficient physical memory mapping can significantly increase BRAM consumption.
- Further optimization must balance memory parallelism, resource utilization, and latency.

## 5. Conclusion & Future Work

### Key Findings

1. **Hardware Reuse**
   - Reduced computational parallelism.
   - Increased total latency by approximately 50.5%.
   - LUT utilization remained a concern.

2. **Arithmetic Bitwidth Optimization**
   - Reduced the intermediate MAC accumulator from 32 to 19 bits.
   - Reduced the phase accumulator from 32 to 24 bits.
   - Aimed to reduce arithmetic hardware overhead without changing numerical results.

3. **Weight Memory Banking**
   - Achieved a significant reduction in LUT utilization.
   - Increased BRAM consumption beyond the hardware budget.
   - Exposed a resource trade-off requiring further investigation.
